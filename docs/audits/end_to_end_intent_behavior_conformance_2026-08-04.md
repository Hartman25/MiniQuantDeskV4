## 2. Bottom-line classification

```text
NONCONFORMANT
```

**Basis.** Three confirmed, load-bearing invariant violations exist with a direct path to either a duplicate live order, a double-counted fill (corrupted durable accounting), or a broker fill silently discarded from durable truth — all matching this audit's own CATASTROPHIC/HIGH definitions — plus a cluster of secondary fail-open regressions (autonomous finalization, operator-truth surfaces, a weaker-than-documented live-capital gate) that independently erode the platform's own stated fail-closed doctrine. None of these are hypothetical: two are reproduced by the repository's own existing tests (which pass, and whose passing assertions *are* the violation), one is the same bug pattern the repository already fixed once in production for a sibling code path (migration `0040`, terminal fills) and left open for the adjacent case (partial fills). This is not a mechanical-cleanliness or documentation gap — it is a behavior mismatch between stated intent and implemented code on the primary orders/fills path, which is exactly what CONDITIONALLY CONFORMANT excludes ("no confirmed unsafe behavior"). Full detail: §8, §14.

Baseline intent, reconciled from `docs/INSTITUTIONAL_READINESS_LOCK.md`, `docs/runbooks/operator_workflows.md`, `docs/runbooks/autonomous_paper_ops.md`, `README.md`/`README_TECHNICAL.md`, and the current Bundle 5/6/7 closure docs:

- Canonical durable chain: outbox enqueue → broker submit → broker ack/fill → inbox → portfolio (CLAUDE.md). No synthetic broker lifecycle events; broker is sole source of truth for order state.
- Bundle 3 (autonomous daily operations) and Bundle 4 (durable paper portfolio/P&L) are accepted-complete on `main`. Bundle 5 (runtime opportunity allocation) reached implementation-and-closure-proof-complete on a separate branch, not merged to the audited `main` SHA at the time of Bundle 5's own writing — but per `git log` at the audited SHA, Bundle 5/6/7-lineage commits (`RUNTIME-OPPORTUNITY-ALLOCATION-01-READINESS-AND-AUTHORITY-REPAIR-01`, multi-strategy conflict policy, dynamic strategy/symbol selection Phase 7A-7C) are present on `main` at HEAD `537e048f`, i.e. materially ahead of the `README_TECHNICAL.md` snapshot dated 2026-07-20 read during this audit. **This is a real drift**: the technical README's own "Current proved posture" section is stale relative to HEAD and should not be treated as current status without cross-checking `git log` — consistent with `docs/INSTITUTIONAL_READINESS_LOCK.md`'s own evidence-hierarchy rule that docs never override code truth.
- Only supported live-broker lane per every runbook read: Paper + Alpaca, single-symbol-or-approved-watchlist, long-only-or-short-per-current-gates, actively supervised. Unattended soak explicitly not started. Live capital explicitly not authorized by any runbook.

Implementation trace, stage by stage (full file:line detail is in §7/§8/§13; this section states the mechanism only):

1. **Strategy → intent**: `StrategyHost::on_bar` (`mqk-strategy/src/host.rs:51`) is pure. `bar_result_to_decisions` (`mqk-daemon/src/decision.rs:275`) derives `decision_id = UUIDv5(run_id:strategy_id:symbol:side:qty:now_micros)`. `now_micros` is live wall-clock (`mqk-daemon/src/state/loop_runner.rs:945`), read once per tick, shared across all symbols in that tick.
2. **Admission/risk**: 12 sequential gates (`decision.rs`, Gate 0 through Gate 7) run before any outbox write; every gate that reads capital/risk/registry/DB state fails closed on absence (no `.unwrap_or_default()` found on any risk value).
3. **Outbox enqueue**: `mqk_db::outbox_enqueue` (`mqk-db/src/orders.rs:199`), `INSERT ... ON CONFLICT (idempotency_key) DO NOTHING`, unique index `uq_outbox_idempotency` (`migrations/0010`).
4. **Atomic claim**: `outbox_claim_batch` (`mqk-db/src/orders.rs:246`), single CTE `... FOR UPDATE SKIP LOCKED ... UPDATE ... RETURNING`, compile-time-gated `OutboxClaimToken`.
5. **Broker submit**: `BrokerGateway::submit_with_context` (`mqk-execution/src/gateway.rs:355`) — the only production caller of `AlpacaBrokerAdapter::submit_order`; requires the claim token and passes `IntegrityGate → RiskGate → ReconcileGate` (`gateway.rs:331`).
6. **Ack/event ingestion**: WS is authoritative (`mqk-runtime/src/alpaca_inbound.rs`), REST `fetch_events` runs on **every** tick regardless of gap state (`mqk-runtime/src/orchestrator.rs:1002`), contradicting `broker_rules.md`'s "gap recovery only" contract — this is the root cause of the terminal-fill double-apply bug already fixed once (migration `0040`) and the open partial-fill analog (§8, A2-FIND-003).
7. **Inbox**: `inbox_insert_deduped_with_identity` (`mqk-db/src/inbox.rs:135`), three layered unique constraints, insert and apply are two separate statements tied together by an `applied_at_utc IS NULL` replay contract, not one DB transaction.
8. **Portfolio apply**: `apply_fill_step`/`apply_entry` (`mqk-runtime/src/orchestrator/apply.rs:195`, `mqk-portfolio/src/accounting.rs:23`) — FIFO, `i128`-intermediate exact arithmetic, single legitimate call site for live trading.
9. **Reconcile**: three independent fail-closed enforcement points (`mqk-runtime/src/orchestrator.rs` Phase 0c; `mqk-reconcile/src/gate.rs` arm/start gates; periodic `reconcile_tick`), monotonic watermark (`mqk-reconcile/src/watermark.rs:122`).
10. **Durable final state / operator truth**: `runs` table + `sys_autonomous_daily_operations` (finalization) + a well-built `truth_state` framework in the GUI (`mqk-gui/src/features/system/truthRendering.ts`), with two confirmed leaks (§11).

## 6. Durable state-machine trace

- **Outbox**: `PENDING → CLAIMED → DISPATCHING → SENT → ACKED/FAILED`, plus `AMBIGUOUS` (quarantine, migration `0020`). Value-legality and claim-metadata-consistency are DB CHECK-enforced (migration `0014`). Transition-graph legality is enforced per-function via `WHERE status = '<expected>'` predicates (a durable CAS pattern) for every function *except* `runs.status`, which uses check-then-act with no `WHERE`-clause guard (§7).
- **OMS order**: `Open, PartiallyFilled, Filled, CancelPending, Cancelled, ReplacePending, Rejected` (`mqk-execution/src/oms/state_machine.rs:44`). Terminal states cannot un-terminal (proven, §8 I12). **`(Open, Fill)` is a legal, unguarded transition** — `OmsOrder::new` starts in `Open` at the moment of synchronous broker `SENT` confirmation, before any WS/REST `Ack` event is necessarily applied. `execution_rules.md`'s literal text ("A `pending` order must not move to `filled` without an intermediate `ack`") is **not enforced as written** — the codebase's functional interpretation (synchronous submit response ≡ acknowledgment) is internally consistent but is not what the rule states, and no test asserts the literal reading. This is not scored as a numbered invariant (not one of I01–I28) but is recorded here per the mission's evidence-hierarchy discipline: code, not the rule's prose, is what runs.
- **Broker cursor**: two independent lanes (`trade_updates` for WS, `rest_activity_after` for REST), confirmed never cross-advanced (`mqk-broker-alpaca/src/types.rs:62`). `Live → ColdStartUnproven` demotion on restart is real (`mqk-daemon/src/state.rs:1461`), but a second writer (`build_execution_orchestrator`, `orchestrator_build.rs:257`) re-derives the same field from a raw, non-demoting DB read after the gate has already passed — currently self-consistent by call-ordering, not by design consolidation.
- **`sys_autonomous_daily_operations`**: the best-built state machine in the repository — real optimistic-CAS `UPDATE ... WHERE state=$x AND state_version=$y` in the same transaction as its append-only event row (`mqk-daemon/src/state/autonomous_daily_operation.rs`). This is the pattern `runs.status` should also use and currently does not (§7).

## 8. Failure-chain analysis

**A2-FIND-001 — Duplicate live order via wall-clock-salted decision identity (I01, I05, I04).**
Trigger: strategy target position unmet across two or more consecutive 1-second ticks (e.g., an outbox row is claimed but the order has not yet filled, or a crash orphans a `CLAIMED` row per I04) → `bar_result_to_decisions` (`decision.rs:275`) recomputes the same economic decision each tick, seeded with a fresh `Utc::now().timestamp_micros()` (`loop_runner.rs:945`) → a *different* `decision_id`/`idempotency_key` each time → `uq_outbox_idempotency` cannot deduplicate different keys → a second outbox row is enqueued and independently dispatched → **wrong action**: two live broker orders for one logical decision → persists across restart (nothing about restart clears the risk; if anything, an orphaned `CLAIMED` row from a crash compounds it) → **financial consequence**: doubled position size / doubled market exposure for one strategy decision → **current detection**: none at submission time; only reconcile drift would eventually surface a broker-vs-internal mismatch, after both orders are already live → **current containment**: `MAX_AUTONOMOUS_SIGNALS_PER_RUN=100` bounds the total, not the specific duplicate → **recovery path**: manual operator reconcile/flatten → **missing proof**: no test exercises "same logical decision, two different `now_micros` values" end to end. Severity: **CATASTROPHIC** (matches this audit's own definition: "duplicate/unwanted live order"). Confidence: **CONFIRMED** (source-proven mechanism; the enabling gap — no in-flight-order accounting in the per-tick loop — is directly read, not inferred; corroborated independently by two research passes, R1 and R8).

**A2-FIND-002 — Orphaned `CLAIMED` outbox row after crash between claim and dispatch (I04).**
Trigger: process crash between `outbox_claim_batch` succeeding and `outbox_mark_dispatching` writing → row is left `CLAIMED` forever → wrong intermediate state: neither re-claimable (`outbox_claim_batch` only matches `PENDING`) nor quarantined (Phase-0b's restart filter matches `AMBIGUOUS`/`DISPATCHING`/unmapped-`SENT`, not `CLAIMED`) → persists indefinitely across restart, silently, until a human reads `GET /api/v1/execution/outbox` or calls `outbox_list_unacked_for_run` directly → financial consequence: none by itself (the row never reached the broker), but it sets up A2-FIND-001 if the same logical decision is re-derived and dispatched while the original sits orphaned, and a later uncoordinated manual `outbox_release_claim` on the stale row (the only exposed release primitive besides the never-wired reaper) can create a second live order → current detection: read-only supervisor listing only, no alert → containment: none automatic → recovery: `outbox_reset_stale_claims` exists, is unit-tested, and is simply never called from any production path → missing proof: none needed — the repository's own test (`scenario_crash_between_claim_and_submit.rs`, re-run by this audit, passes) proves the stuck state as its designed assertion. Severity: **HIGH**. Confidence: **CONFIRMED** (test-executed by this audit).

**A2-FIND-003 — WS/REST dual-lane double-apply on partial fills (I08, I09, I13, I28; contradicts `broker_rules.md`).**
Trigger: Alpaca delivers the same economic partial fill on both lanes while WS continuity is `Live` (the code's own documented, ongoing design — `mqk-broker-alpaca/src/lib.rs:37-42` — not an edge case) → WS row carries `broker_fill_id=None`, REST row carries `broker_fill_id=Some(activity.id)`, and each has a distinct `broker_message_id` (timestamp differs by lane) → neither of the two dedupe constraints fires (`uq_inbox_run_broker_fill_id` is null-exempt; `uq_inbox_run_order_single_fill` explicitly excludes `partial_fill`) → both rows insert, both apply → wrong state: cash/position moved twice for one real execution → persists across restart (§I28 — replay faithfully reproduces the duplicate) → financial consequence: silently inflated position size and incorrect cost basis for that symbol → current detection: `check_capital_invariants` cannot catch it (both sides replay the identical duplicated ledger); only broker-side reconcile drift would eventually flag a position mismatch, after the fact → containment: none at the apply layer → recovery: manual operator investigation via reconcile mismatch tooling → missing proof: zero tests exercise "same fill, two lanes, two identities" (confirmed by grep across the OMS and orchestrator test suites). This is not a novel risk: migration `0040`'s own commit comment documents that this *exact* pattern already caused a real double-apply for **terminal** fills in production, and was fixed there by `uq_inbox_run_order_single_fill` — a fix that was then explicitly scoped to exclude partials. Severity: **CATASTROPHIC** (matches this audit's definition: "corrupted durable accounting"). Confidence: **CONFIRMED** (source-proven, with a documented production precedent of the identical bug pattern in the adjacent case).

**A2-FIND-004 — Unknown-order fills fail open, not closed (I16).**
Trigger: a broker fill arrives for an `internal_order_id` absent from the current run's in-memory OMS map (a genuinely unrecognized/misattributed fill, not distinguished from a benign historical fill from this run's own prior orders) → `is_historical_fill_no_run_ownership` matches both cases identically → Phase 2: the event is never even inserted into `oms_inbox` (no durable record at all) → Phase 3 (WS path): inserted, then marked applied with no OMS effect, an `info`-level log line only → wrong state: an economically real fill is dropped from durable truth → persists across restart (nothing recovers what was never recorded) → financial consequence: a real fill is simply missing from the system's books, understating true position/exposure → current detection: none beyond an `info` log → containment: none — this was a **deliberate, tested change away from a prior halt-on-unknown-fill design** (`ORPHAN-WS-FILL-HALT-01`), re-confirmed by this audit's direct re-execution of `scenario_unknown_order_fill_halt.rs`, which passes and whose own test header documents the design change → recovery: none automatic; requires the same reconcile-drift path as A2-FIND-003 to eventually surface the discrepancy. Severity: **HIGH** (matches "missed ... fill"). Confidence: **CONFIRMED** (test-executed by this audit; the design change itself is intentional and documented, which sharpens rather than weakens the finding — it is a ratified regression against CLAUDE.md's fail-closed mandate, not an oversight, and appears never to have been re-evaluated against that mandate).

**A2-FIND-005 — Autonomous daily finalization can certify "completed with activity" without confirming order resolution (I27), compounded by silent WS-drop-after-stop (I19).**
Trigger: an order reaches `SENT`/`ACKED` → run is stopped (by operator or session-controller boundary) before the order's terminal event (fill/cancel/reject) arrives → the terminal WS frame, if it arrives after `active_owned_run_id()` was cleared, is silently dropped (`alpaca_ws_transport.rs:471`, no log, no persistence) → the daily finalizer's `any_broker_reach` check (`autonomous_daily_outcome.rs:785`) is satisfied by the earlier ACK alone → the day is durably finalized `CompletedWithActivity` → wrong state: a day is marked resolved while an order's true broker-side outcome (filled? still open? canceled?) was never captured → financial consequence: none directly (no wrong order/fill), but the durable historical record is materially misleading and any downstream accounting/reconciliation that trusts "finalized" as "resolved" inherits the gap → detection: none — this is exactly the terminal, DB-committed state operators are told to trust (§16b of the autonomous ops runbook) → recovery: none — finalization is documented as immutable after commit ("read-only history from this point"). Severity: **HIGH** (misleading durable operator/history truth on the primary daily-operation surface). Confidence: **CONFIRMED** for both halves independently (source-proven); the compound chain is **PLAUSIBLE** (not reproduced end-to-end by a single test, but each link is independently proven).

**A2-FIND-006 — `risk_summary.kill_switch_active` fails open on a DB read error (I21).**
Trigger: DB reachable enough to serve other reads, but the specific `sys_risk_block_state` query fails or times out → `load_risk_block_state(...).ok().flatten()` (`routes/portfolio.rs:654`) collapses "no row" and "query error" into the same `None` → `risk_blocked` computed as `false` → GUI renders "Kill switch: Inactive" in green (`RiskScreen.tsx:46`, no null/unknown branch exists) → operator could resume/arm believing risk is clear when it is genuinely unverified → detection: none, the panel-level hard-block in `truthRendering.ts` explicitly does not gate on this field (comment confirms `/risk/summary` "never lands in missingEndpoints") → recovery: none automatic. Severity: **HIGH** (a fail-open safety-status surface an operator is explicitly instructed to check before arming, per `operator_workflows.md` §1b). Confidence: **CONFIRMED** (source-proven, both API and GUI sides read directly).

**A2-FIND-007 — `LiveCapital` trust gate checks evidence-file validity, not trust completeness (I24).**
Trigger: an operator (or a misconfigured automation) supplies real live Alpaca credentials, a genuinely-established live WS session, an operator token, and a structurally valid (but, by the Python pipeline's own permanent design, always `live_trust_complete=false`) parity-evidence file → `ParityEvidenceGateStatus::is_start_safe()` (`parity_evidence.rs:147`) returns `true` for `Present{live_trust_complete: false, ..}` because it never inspects that field → `LiveCapital` start proceeds past the one gate specifically documented as existing to block this → the advisory `evaluate_mode_transition` function that *does* check this is wired only to a different (hot-transition) route, never the cold-start path actually used. Severity: **HIGH** (this is a designed safety ceiling that does not do what its own comments claim; CLAUDE.md states real money will be deployed and treats all decisions accordingly). Confidence: **CONFIRMED** (source-proven; not currently exploitable without an operator independently supplying real live credentials and consciously proceeding through every other gate — this is a policy-integrity gap, not a demonstrated live-order path today).

## 12. Operator-truth analysis

The GUI/API truth-state framework (`truthRendering.ts`, `panelTruthRenderState`, `isTruthHardBlock`) is unusually disciplined and correctly wired into every major screen checked (Execution, Risk denials, Reconcile, Portfolio, Autonomous Daily Operations) — hard-blocking on unavailable/no-snapshot/unimplemented/not-wired truth states before rendering domain data, consistently. Severity: **MEDIUM**. Confidence: **CONFIRMED**.

Causality-ID propagation is good on durable/pre-dispatch surfaces (`run_id`, `client_order_id` well-propagated) but `strategy_id` is hardcoded `None` on every *live* order/position/fill/denial route (`OrderSnapshot` has no such field structurally), meaning an operator cannot trace a live open order or position back to its originating strategy without manually cross-referencing the durable outbox surface — a real multi-strategy operability gap, not a fabrication risk. Severity: **LOW**. No violation found in the no-trade/refusal-cannot-claim-a-trade check (I23) or the read-only-cannot-mutate check (I22, not exhaustive — routing-table level only).
